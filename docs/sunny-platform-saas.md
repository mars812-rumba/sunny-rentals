# Sunny Platform: SaaS для проката транспорта

Статус: концепция и план реализации  
Дата: 2026-10-08  
Подход к данным первого этапа: JSON/JSONL с последующей миграцией в PostgreSQL

## 1. Видение продукта

Sunny Platform — операционная система для небольших и средних прокатов транспорта.

Первый эталонный вертикальный продукт — аренда автомобилей. После стабилизации ядро должно поддерживать электросамокаты для курьеров, мотоциклы, байки, квадроциклы, снегоходы и другие виды арендуемого транспорта.

Продукт состоит из трёх контуров:

```text
Sunny Super Admin
  -> подключение и управление прокатами

Tenant Workspace
  -> рабочий кабинет конкретного проката

Public Storefront
  -> витрина и бронирование для клиента
```

## 2. Стратегический принцип

На первом этапе нельзя превращать интерфейс автомобилей в полностью абстрактный конструктор. Авто остаётся эталонным шаблоном с лучшим UX, SEO и бизнес-логикой.

При этом внутреннее ядро строится вокруг `RentalAsset`, а не `Car`:

```text
RentalAsset
  id
  tenant_id
  asset_type
  name
  status
  photos
  pricing_profile
  availability_profile
  deposit_policy
  location
  specs
```

`asset_type` на первом этапе:

- `car`;
- `electric_scooter`;
- `motorcycle`;
- `bike`;
- `atv`;
- `snowmobile`;
- `other`.

UI, фильтры и обязательные характеристики задаются вертикальным профилем, а не одним универсальным экраном.

## 4. JSON-first архитектура

```text
data/
  platform/
    tenants.json
    users.json
    memberships.json
    subscriptions.json
    audit.jsonl

  tenants/
    <tenant_id>/
      tenant.json
      members.json
      assets.json
      customers.json
      bookings.jsonl
      payments.jsonl
      maintenance.jsonl
      conversations.jsonl
      analytics.jsonl
      settings.json
      integrations.json
```

Каждая запись обязана содержать:

```json
{
  "id": "entity_unique_id",
  "tenant_id": "sunny-rentals",
  "schema_version": 1,
  "created_at": "2026-10-08T00:00:00Z",
  "updated_at": "2026-10-08T00:00:00Z"
}
```

### Требования к JSON-слою

- доступ только через repository-интерфейсы;
- атомарные записи;
- блокировки;
- Pydantic-модели;
- валидация `tenant_id`;
- версионирование схем;
- миграции форматов;
- резервные копии;
- soft delete и архив;
- отсутствие прямого чтения файлов из HTTP endpoints.

Позднее реализации репозиториев заменяются с JSON на PostgreSQL без изменения API-контрактов.

Технический контракт Sprint 1 и точная карта перехода текущих Sunny JSON
зафиксированы в [`sunny-saas-data-contracts.md`](./sunny-saas-data-contracts.md).

## 6. Суперадминка

### Главный дашборд

- все прокаты;
- триалы и истекающие триалы;
- активные и приостановленные подписки;
- посетители;
- заявки;
- подтверждённые и отменённые брони;
- конверсия;
- потенциальный оборот;
- ошибки интеграций.

### Онбординг проката

Онбординг поддерживает два равноправных сценария:

- **done-for-you**: суперадминистратор сам создаёт парк, заполняет настройки,
  импортирует транспорт, настраивает цены и передаёт владельцу готовый кабинет;
- **совместный**: суперадминистратор создаёт каркас и приглашает владельца
  закончить заполнение самостоятельно.

Самостоятельная регистрация владельца не является обязательной для запуска.

1. Название, slug, страна, язык, валюта и часовой пояс.
2. Тип транспорта и вертикальный шаблон.
3. Владелец и приглашение.
4. Тариф и семидневный триал.
5. Логотип, контакты и домен.
6. Импорт транспорта.
7. Цены, депозит, доставка и условия.
8. Telegram/AI-интеграции.
9. Тестовая бронь.
10. Публикация.

Суперадминистратор может выполнить все десять шагов от имени конкретного
тенанта. Каждое такое действие записывается в аудит с `tenant_id`, actor и
временем; владелец видит уже готовую витрину и при необходимости меняет её.

### Карточка тенанта

- состояние подписки;
- срок триала;
- владелец и сотрудники;
- количество транспорта;
- активные брони;
- ссылка на витрину;
- интеграции;
- аудит;
- вход от имени владельца с обязательной записью события.

## 9. Триал

Рекомендуемая модель:

- семь календарных дней после публикации витрины или принятия приглашения владельцем;
- серверная проверка прав на каждую операцию;
- уведомления за три дня и за один день;
- после завершения — кабинет только для чтения;
- данные сохраняются;
- новые бронирования блокируются либо витрина переводится в режим запроса контакта;
- суперадмин может продлить триал вручную.

Финальная политика поведения витрины после триала должна быть подтверждена отдельно.

## 11. Граница платформы

Sunny Platform не должна сразу становиться универсальной системой для любого бизнеса.

Рекомендуемая структура продуктового портфеля:

```text
Общий platform-control-plane
  tenants / auth / roles / billing / domains / analytics / audit

Rental vertical
  автомобили / самокаты / мотоциклы / другой транспорт

Food vertical
  меню / корзина / приготовление / заказ еды

Commerce vertical
  каталог Loft Fire / заявки / производство или продажа
```

Приоритет разработки — Rental vertical. Foodmarket сохраняется как отдельный экспериментальный продукт и потенциально использует общий control plane после его стабилизации.

- несколько заявок одного клиента;
- отмена заявки клиентом;
- календарь и защита от конфликтующих броней;
- CRM и история коммуникаций;
- бессрочное накопление уникальных контактов из бота и витрины;
- единый поиск по активным и архивным лидам без потери Telegram ID;

- публичный API для партнёров.

Эти функции добавляются после первого успешного внешнего пилота.

## 13. План реализации

### Спринт 0 — зафиксировать продуктовые решения

Результат: утверждённые правила, которые не придётся менять во время разработки.

- название платформы;
- схема URL пилотных витрин;
- момент начала триала;
- поведение после окончания триала;
- общий или отдельный Telegram-бот;
- роли владельца и сотрудников;
- какие настройки суперадмин может менять от имени парка;
- какие данные суперадмин обязан заполнить при подключении парка «под ключ»;
- минимальная аналитика;
- политика удаления и хранения данных.

### Спринт 1 — tenant foundation и JSON-контракты

Результат: существующий Sunny становится первым тенантом новой модели.

- определить Pydantic-модели сущностей;
- добавить `schema_version`;
- создать `TenantContext`;
- создать repository-интерфейсы;
- реализовать атомарные JSON/JSONL repositories;
- разделить данные по `tenant_id`;
- добавить мигратор текущих файлов Sunny;
- добавить проверки невозможности межтенантного чтения;
- настроить резервное копирование и восстановление;
- убрать секреты из исходного кода.

Критерий завершения: API получает tenant из доверенного контекста, а не из произвольного поля запроса.

Дополнительный критерий: первый вход обычного пользователя в Telegram-бот
создаёт долговечную карточку лида. Архивация убирает её из активной CRM, но не
удаляет контакт из общей истории и будущей SaaS-миграции.

### Спринт 2 — авторизация и роли

Результат: суперадминистратор и владелец парка входят в разные кабинеты и имеют разные права.

Статус control plane: короткоживущие подписанные сессии platform admin и
закрытые API создания, просмотра и публикации tenant уже реализованы отдельно
от основной логики приложения. Вход проверяет подпись `initData` выделенного
Telegram Mini App, срок её действия и Telegram ID по allowlist. После проверки
Mini App может выдать одноразовый 60-секундный handoff в полноценный браузерный
кабинет; код передаётся во фрагменте URL, уничтожается после первого обмена и
выдаёт отдельную рабочую сессию. Password-login отсутствует. Маршруты подключаются только при
`PLATFORM_ADMIN_API_ENABLED=true`; по умолчанию control plane выключен, а при
неполной конфигурации отказывается запускаться.

- пользователи;
- безопасные сессии;
- приглашение владельца;
- роли `owner`, `manager`, `operator`, `viewer`;
- middleware авторизации;
- проверка роли на каждом административном endpoint;
- журнал входов и чувствительных действий;
- безопасное переключение суперадминистратора в контекст тенанта.

Критерий завершения: владелец одного парка не может увидеть ID, клиентов, транспорт или брони другого парка.

### Спринт 3 — суперадминка

Результат: новый парк можно создать без ручного копирования папок и редактирования JSON.

Статус backend-ядра: создание draft-тенанта, владельца, структуры JSON,
отложенного trial и атомарный rollback уже реализованы. Защищённый HTTP API
готов, но feature flag по умолчанию выключен. Первый интерфейс по маршруту
`/platform-admin` уже реализует Telegram-вход, безопасный переход из Mini App в
обычный браузер, реальный список прокатов, создание draft-тенанта и
подтверждаемую публикацию с запуском триала. Контур
можно включать только в явно настроенном окружении; production по умолчанию его
не публикует.

- список тенантов;
- создание и редактирование парка;
- статусы `draft`, `trialing`, `active`, `suspended`;
- начало и продление триала;
- приглашение владельца;
- выбор автомобильного шаблона;
- импорт автомобилей;
- проверка заполненности;
- предпросмотр витрины;
- публикация;
- состояние Telegram и других интеграций.

Критерий завершения: тестовый парк создаётся через интерфейс и получает рабочую витрину без доступа к серверным файлам.

### Спринт 4 — кабинет владельца парка

Результат: владелец самостоятельно управляет ежедневной работой.

- дашборд;
- автопарк;
- карточка автомобиля;
- тарифы и доступность;
- календарь;
- заявки и бронирования;
- клиенты и CRM;
- отмены и повторные заявки;
- настройки компании;
- сотрудники;
- история действий.

Критерий завершения: владелец может добавить автомобиль, принять бронь, изменить статус и закрыть аренду без помощи суперадминистратора.

### Спринт 5 — мультитенантная витрина

Результат: каждый парк имеет изолированную брендированную витрину.

- определение тенанта по URL;
- тема, логотип и контакты;
- каталог конкретного тенанта;
- даты и доступность;
- корректные цены;
- отправка заявки;
- несколько броней одного клиента;
- отмена клиентом через подписанную ссылку или авторизованную сессию;
- локализованные условия аренды;
- отдельные SEO metadata и canonical;
- защита от попадания чужих данных в кэш.

Для пилота допускается path-based URL. Поддомены и собственные домены добавляются после проверки модели.

### Спринт 6 — аналитика и триал

Результат: суперадминистратор и владелец видят реальную воронку, а ограничения триала работают на backend.

- приём аналитических событий;
- anonymous/session ID;
- источники и UTM;
- посетители, просмотры транспорта и поиски дат;
- начатые, отправленные и подтверждённые заявки;
- отмены;
- конверсия;
- срок триала;
- уведомления об окончании;
- серверные entitlement-проверки;
- ручная активация подписки.

Критерий завершения: цифры дашборда можно сверить с тестовыми сессиями и журналом броней.

### Спринт 7 — внешний пилот

Результат: один реальный сторонний автопарк работает на платформе.

- выбрать design partner;
- провести интервью и собрать исходные данные;
- импортировать парк;
- обучить владельца;
- провести тестовые брони;
- включить витрину;
- ежедневно проверять ошибки и воронку;
- фиксировать все ручные операции;
- по итогам отделить обязательные функции от индивидуальных пожеланий.

После стабильного пилота подключаются ещё два-три парка, но уже по одинаковому процессу.

### Спринт 8 — продуктовая упаковка

Результат: платформу можно предлагать следующим клиентам без индивидуальной разработки.

- тарифы;
- лендинг для владельцев парков;
- демо-режим;
- чек-лист онбординга;
- база знаний;
- шаблон импорта;
- политика поддержки;
- метрики здоровья тенанта;
- процесс оплаты и продления;
- SLA для критических ошибок.

### Спринт 9 — электросамокаты для курьеров

Результат: второй вертикальный шаблон подтверждает универсальность rental-ядра.

- профиль `electric_scooter`;
- недельные и месячные тарифы;
- график платежей;
- закрепление за курьером;
- аккумуляторы и зарядные устройства;
- ремонты и замены;
- просрочка;
- специализированная витрина;
- специализированный кабинет оператора.

## 14. Критерии готовности к выходу в люди

Платформа готова к первому внешнему пилоту, если одновременно выполнены условия:

1. Новый парк создаётся через суперадминку.
2. Все данные имеют `tenant_id` и проходят серверную проверку.
3. Автоматические тесты подтверждают отсутствие межтенантного доступа.
4. Владелец видит только свой парк.
5. Клиент может отправить несколько заявок и отменить нужную заявку.
6. Конфликтующие даты не создают двойную подтверждённую бронь.
7. Telegram-уведомление приходит правильному парку.
8. Триал ограничивается на backend.
9. Есть ежедневная резервная копия и проверенная процедура восстановления.
10. Суперадмин видит воронку от посещения до подтверждённой брони.
11. Ошибка одного тенанта не раскрывает данные другого.
12. Все административные изменения записываются в аудит.

## 15. План пилотного запуска

### Первый design partner

Искать не самый крупный парк, а владельца, который:

- лично участвует в операционной работе;
- готов быстро давать обратную связь;
- уже получает заявки из Telegram, WhatsApp, Avito или сайта;
- имеет понятный парк и актуальные цены;
- согласен провести тестовый запуск на ограниченном трафике.

### Формат предложения

- ручное подключение;
- семь дней полного доступа;
- помощь с импортом;
- брендированная витрина;
- CRM, календарь и уведомления;
- совместный разбор воронки;
- специальная цена первого клиента после триала.

### Что измерять

- время подключения парка;
- количество ручных исправлений;
- время до первой опубликованной машины;
- время до первой заявки;
- долю заявок, обработанных владельцем без помощи;
- конверсию в подтверждение;
- отмены;
- ошибки доступности и цен;
- функции, без которых владелец отказывается продолжать.

## 16. Решения, которые нужно утвердить перед разработкой

Рекомендуемые стартовые значения:

1. Триал начинается при публикации витрины, а не при создании тенанта.
2. После триала кабинет становится доступен только для чтения, новые заявки блокируются.
3. Оплата подписки на первом пилоте активируется вручную суперадминистратором.
4. Для пилота используется общий Telegram-бот с маршрутизацией по тенанту.
5. Первый URL — path-based; поддомены вводятся после пилота.
6. Владелец может приглашать менеджеров, но не менять тариф и системные интеграции.
7. Физическое удаление данных недоступно из обычного интерфейса.
8. Sunny Rentals мигрирует первым и служит эталонным тенантом.

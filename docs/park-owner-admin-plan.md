# Кабинет владельца парка — согласованный порядок работ

Приоритет: **сначала клиентская витрина по образцу Sunny `/app`**, затем кабинет
владельца. Новую админку с нуля не строим: адаптируем существующие блоки Sunny.

Владелец здесь — владелец проката/тенанта, не владелец отдельного автомобиля.
Он управляет всем своим парком. Один уровень доступа для команды парка, без
новой матрицы ролей и согласования каждого изменения с суперадминистратором.

## Актуальная граница пилота (10 октября 2026)

Приоритет уточнён владельцем: подготовить 5 машин нового парка, показать
хорошую клиентскую витрину, дать владельцу управление автопарком и наглядную
занятость. Суперадминистратор видит все парки и их триалы. CRM, офферы,
четвёртая вкладка и дальнейшее расширение — после проверки интереса парков.
Не строим заранее универсальный конструктор: тип техники уже настраивается
у парка/машины, валюта и часовой пояс принадлежат парку. Общие аренда и
занятость переиспользуются; специальные поля других вертикалей — по запросу.

## Порядок после клиентской витрины

1. Автопарк: карточки Sunny, создание/редактирование машины, фотографии,
   характеристики, депозит, публикация. Основы: `CarsPage.tsx`, `CarForm.tsx`.
2. Цены: существующие редакторы сезонов и сроков, хранение внутри парка;
   подключение к серверному расчёту и клиентской витрине. Не только UI полей.
3. Календарь: `MonthCalendarView.tsx`, `SchedulerCalendar.tsx`, формы брони;
   месяц и Гант, заявки, ручное создание, подтверждение/отмена.
4. **Отложено до обратной связи пилота:** CRM/офферы с клиентами только данного парка.
   Предложение клиенту и созданная бронь — разные сущности, не объединять.
5. Telegram-уведомления владельцу и клиенту, сквозная проверка сценариев.

Навигация пилота: **Автопарк · Календарь**. CRM не показываем как пустой раздел.
Четвёртая вкладка **Общая информация**
отложена; пустую вкладку пока не показываем. Её наполнение согласовать отдельно.

## Что значит «переиспользовать»

Внешний вид, компоненты и сценарии остаются привычными. Но прямые обращения
старых страниц к общим `/api/cars`, `/api/admin/cars`, броням, владельцам и CRM
заменяются tenant-aware операциями. Контекст парка проверяется сервером;
фильтр интерфейса не является защитой. Ключи кэша также должны включать парк.
Общие компоненты получают данные/действия через адаптеры, не дублируют хранилища.

## Критерий готовности каждого раздела

Привычный интерфейс + сохранение данных + чтение на витрине/в календаре +
проверка изоляции двух парков. Существующий Sunny продолжает работать.
Нет автоматического переноса его рейтингов, тарифов, доставки, документов
или коммерческих обещаний в другой парк.

## Первый рабочий шаг — автопарк владельца

Реализован начальный доступ через блок «Автопарк владельца» в Telegram-витрине.
Пока это не отдельная трёхвкладочная админка. Создание/изменение машин, марка,
модель, год, цвет, суточная ставка, депозит, публикация, загрузка фото и архив
используют общий редактор `PlatformTenantWorkspace.tsx`. Карточки используют
общую оболочку `VehicleCardFrame.tsx`. Это начальный шаг, не полное совпадение
редакторов с `CarsPage`/`CarForm`: топливо, коробка, сезоны и другие поля — далее.

`ParkOwnerFleet.tsx` открывает контекст парка; `park-owner-fleet.ts` отправляет
свежую Telegram `init_data` в теле POST, без ключа суперадмина и без подписи
в URL. `/api/partners/fleet/{list,save,archive,photo,media}` повторно проверяет
владельца. `TenantAssetAdmin.for_owner` использует те же JSON, аудит, обработку
фотографий и архивирование, без выдачи прав платформы. Перед записью права
повторно проверяются под общей блокировкой. Логотип и подключение бота остаются
в суперадминке. Чужие машины/медиа и клиентский аккаунт не имеют доступа.

Проверка владельцем после публикации: открыть парк через личное приглашение,
раскрыть «Автопарк владельца», создать скрытую тестовую машину, загрузить фото,
изменить ставку/депозит, включить публикацию, проверить витрину после обновления,
затем перенести тестовую машину в архив. Архив сохраняет данные и фотографии.

Добавлены `backend/tests/test_park_owner_fleet.py` (создание, изменение, архив,
фото, приватные медиа, отзыв доступа, чужой парк, поддельная роль) и
`tests/park-owner-fleet.test.mjs` (подпись в теле, отсутствие Bearer, multipart,
проверка парка в ответе). SSR проверяет отсутствие платформенных кнопок в режиме
владельца. Сборка выполняется в `/tmp`, без деплоя. Проверка на телефоне и
визуальная проверка настоящего Telegram остаются владельцу после публикации.

## Календарный шаг пилота

`ParkBookingCalendar.tsx` теперь предлагает **Список · Месяц · Гант**, месяц
по умолчанию. Общие `MonthCalendarView.tsx` и `SchedulerCalendar.tsx` Sunny
получают tenant-данные через `utils/park-calendar.ts`, без обращений к старым
глобальным API и без второго хранилища бронирований. Тот же компонент доступен
владельцу через Telegram и суперадминистратору внутри выбранного парка.

Есть выбор месяца, предыдущий/следующий месяц, «Сегодня», фильтр техники,
обновление, детали дня/заявки, подтверждение и отмена с существующей проверкой
ожидаемого статуса. Месяц показывает выдачу, промежуточные занятые дни и возврат;
отменённые заявки остаются в списке, но не в графической занятости. Гант
показывает 97 дней (7 до выбранного начала + 90 после) и строки машин, включая
архивные машины, у которых сохранились брони.

Даты берутся из серверного `pricing.start_date/end_date` — гражданских дат
парка, не из UTC-таймстампов в часовом поясе телефона. Для парка полоса Ганта
использует `[получение, возврат)`: день возврата не занимает полосу. Старый
Sunny сохраняет прежнее поведение по умолчанию. В режиме парка одно нажатие
на полосу открывает детали; доступно открытие с клавиатуры, горизонтальная
прокрутка не запускает выделение новой брони. Фотографии старого Sunny в Ганте
парка не запрашиваются.

**Не включено в этот шаг:** ручное создание/перенос брони в календаре,
drag-and-drop, время выдачи/возврата, сообщения клиенту, автообновление в фоне.
Новые заявки видны после «Обновить календарь» или повторного открытия.
Следующий функциональный шаг — ручная бронь/блокировка занятости владельцем
с серверной проверкой пересечений, не CRM.

## Видимость триала

Сохранённая подписка уже содержит длительность (по умолчанию 7 дней), начало
при публикации и окончание. `trial_summary` формирует только read-only проекцию:
API списка/деталей/публикации парков и приватный автопарк владельца возвращают
эти сроки. `ParkTrialStatus` показывает их в часовом поясе парка; суперадминка
также показывает окончание в списке парков. Повторное чтение не запускает и
не продлевает триал. Флаг окончания вычисляется сервером.

**Автоматическое отключение не реализовано:** пока только видимый срок и
отметка об окончании. Выбор политики (ручное решение или read-only после
окончания) отправлен владельцу на согласование. Данные не удаляются.

Проверки: `tests/park-calendar.test.mjs` проверяет гражданские даты, архивные
строки, границу возврата, старое поведение Sunny, доступные кнопки месяца и
триал; backend-тесты проверяют сроки, изоляцию/авторизацию и отсутствие записи
при чтении. SSR и сборка не заменяют проверку свайпа/касания в Telegram.

Сценарий проверки после отдельной публикации: создать 5 машин → загрузить фото
и цены → опубликовать парк → выдать приглашение владельцу → отправить клиентскую
заявку из бота → обновить календарь у владельца и суперадмина → проверить её
в списке, месяце и Ганте → подтвердить → отменить → проверить освобождение дат.

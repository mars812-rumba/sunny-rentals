# Карточка автомобиля из календаря парка

## Назначение и границы

Нажатие на автомобиль в левой закреплённой колонке календаря открывает карточку только для просмотра: фотографии и хронологию броней этого автомобиля. Это небольшое расширение существующего кабинета Sunny Platform для владельца проката и суперадминистратора, соответствующее `PRODUCT.md`: понятный рабочий интерфейс, изоляция парков и доступность с клавиатуры. Изменение не вводит новую визуальную систему; создавать или менять корневой `DESIGN.md` и глобальные токены для него не требуется.

## Существующая визуальная основа

`ParkVehicleScheduleSheet.tsx` использует `ParkFormSheet` / `ParkFormSheetContent`, а не отдельный тип модального окна. Сохраняются белая поверхность, основной текст slate-900, вторичный slate-600, разделители slate-200 и синий контур клавиатурного фокуса. Название автомобиля — заголовок диалога; госномер показывается только при наличии. Далее идут фотографии и раздел «Брони автомобиля» без редактирования и кнопок изменения брони.

На узком экране это нижняя панель со скруглёнными верхними углами; начиная с существующего порога 640 px — центрированная панель шириной до 48 rem. Локальный класс ограничивает высоту карточки **80dvh**, включая широкие экраны. Заголовок остаётся вне прокручиваемого тела; тело использует внутреннюю вертикальную прокрутку и существующий отступ безопасной зоны. Общий лимит других панелей не меняется.

## Содержимое и достоверность данных

- Фотографии берутся из `asset.photos.main` и `asset.photos.gallery`, с удалением повторов и сохранением порядка. Это горизонтальная лента с привязкой прокрутки; на телефоне соседняя фотография частично видна. При отсутствии данных показано «Фото пока нет». Даты съёмки или загрузки не выдумываются: используемый контракт их не предоставляет.
- Приватные фото загружает существующий `ParkCalendarPhoto` через соответствующий доступу tenant endpoint. Используются временные object URL с отменой запроса и освобождением URL; подстановка старых публичных путей Sunny не применяется. Ошибка фото оставляет существующую заглушку.
- Хронология строится из уже загруженного календарного набора текущего парка, по точному `asset_id`. Это не отдельная загрузка полной истории и не обещание наличия записей за пределами полученного набора. Отменённые и отклонённые записи исключаются; остальные, включая блокировки занятости, сортируются по `start_at`, при равенстве — по ID.
- Каждая запись показывает номер брони (или ID), статус, даты выдачи и возврата. Блокировка подписана как «Блокировка занятости». Имя клиента отображается только при наличии в `customer.name` или `operator_details.customer_name`.
- Даты берутся из `pricing.start_date` / `pricing.end_date`. Время берётся из явно сохранённых данных выдачи/возврата; иначе форматируется из timestamp в часовом поясе брони, с существующим резервным `Asia/Bangkok`. Нераспознаваемый timestamp даёт «—». Статусы используют доступные подписи и локализацию кабинета.

Карточка не создаёт и не изменяет брони, фотографии, автомобиль или данные клиента. Для пустой хронологии есть явное сообщение.

## Интеграция и взаимодействие

В `SchedulerCalendar` необязательный `onCarClick` подключён к настоящей кнопке поверх ячейки автомобиля в режиме `readOnly`. У неё есть доступное имя с названием автомобиля, управление Enter/Space и видимый фокус. Перед открытием кнопка получает фокус, чтобы существующий механизм панели мог вернуть его на исходный автомобиль после закрытия.

`ParkBookingCalendar` хранит выбранный `vehicleId` и через `scheduleVehicle` находит автомобиль в текущем `assets`. Если историческая строка осталась в бронях, а автомобиля уже нет в актуальном парке, карточка всё равно открывается: название берётся из брони, фотографии не выдумываются. Карточке передаются текущие `bookings`, `tenantId` и режим доступа. Переключение tenant/режима доступа пересоздаёт внутреннее состояние календаря. Пока выбрана машина, периодический polling приостановлен существующим условием; это не отменяет другие уже начатые или явно вызванные обновления. После закрытия обычный polling возобновляется при выполнении остальных условий.

Стабильный `openVehicle` создан через `useCallback`; существующие `memo` календаря и `useMemo` тяжёлых представлений сохранены. Сам выбор машины не добавлен в зависимости мемоизированной сетки.

Клавиатурная навигация, модальный фокус, Escape, закрытие через оверлей, возврат фокуса и кнопка «Закрыть» опираются на существующие Radix / `ParkFormSheet` primitives. На телефоне сохраняется ручка панели с нажатием и жестом закрытия; крестик доступен и в этой карточке. Лента фотографий фокусируема и подписана. Существующее отключение анимаций при `prefers-reduced-motion` наследуется из `park-form-sheet.css`.

## Проверки и приёмка

В рамках реализации пройдены 86 целевых Node/SSR-тестов календаря и панели; результат передан основным исполнителем. Эта документационная правка не повторяет запуск тестов. Проверка diff должна оставаться соразмерной изменению.

Playwright/Chromium и браузерные скриншоты не запускались: владелец прямо запретил их по умолчанию для обычных правок сайта. Кодовые проверки не означают визуальную проверку в браузере. После отдельной публикации владелец проверяет открытие из левой колонки, фотографии, хронологию, прокрутку и закрытие на телефоне и широком экране. Публикация, перезапуск сервисов и одобрение визуального результата не входят в эту документационную правку.

Источники: `PRODUCT.md`, `src/components/platform/ParkVehicleScheduleSheet.tsx`, `ParkBookingCalendar.tsx`, `ParkCalendarPhoto.tsx`, `ParkFormSheet.tsx`, `park-form-sheet.css`, `src/components/admin/SchedulerCalendar.tsx`. Метод документации существующего интерфейса сверён с `impeccable/reference/document.md`; локальное поведение карточки не превращается в новые глобальные правила дизайна.

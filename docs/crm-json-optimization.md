# CRM: оптимизация чтения JSON — 31 октября 2026

Без миграции БД и изменения формата/содержимого данных:

- `/api/crm/users` один раз читает бронирования и строит локальный индекс по
  user_id: активная бронь, подтверждённая бронь, последняя бронь.
- Последняя бронь определяется тем же строковым created_at; при равенстве
  остаётся первая запись, как при прежней стабильной сортировке.
- `/api/crm/stats` строит индекс пользователей вместо линейного поиска
  для каждой строки чата; при дубликатах ID сохраняется первая запись.
- Нет межзапросного кэша: следующий запрос заново читает данные, включая
  изменения из другого процесса бота. Чтение списка использует единый
  снимок бронирований вместо сотен потенциально разных снимков.
- Не менялись интервалы обновления, API-контракт, статусы, правила
  непрочитанного, лимиты JSONL, фильтры и интерфейс.

Первый локальный замер на текущих данных, медиана пяти последовательных
вызовов обработчика (без HTTP, авторизации и браузера):

| Обработчик | До | После |
| --- | ---: | ---: |
| get_crm_users, all | 613,48 мс | 23,92 мс |
| get_crm_stats, all | 80,68 мс | 25,55 мс |
| Чтений bookings.json на запрос списка | 560 | 1 |

Это не прогноз времени загрузки всего интерфейса на production.
Сравниваются реальные функции, извлечённые через AST без импорта приложения,
старта фоновых задач, обращения к Telegram и записи в рабочие данные.
Исходник до изменения сохранён только локально:
`/tmp/sunny-crm-before-json-optimization.py`.

Проверки:

```sh
PYTHONPATH=backend backend/venv/bin/python -m unittest discover -s backend/tests -p 'test_crm*.py' -q
PYTHONPATH=backend backend/venv/bin/python -m unittest discover -s backend/tests -p 'test_jsonl_tail.py' -q
PYTHONPATH=backend backend/venv/bin/python backend/tests/test_crm_json_performance.py --benchmark-before /tmp/sunny-crm-before-json-optimization.py
```

Новые тесты проверяют один проход, прежние правила бронирований, одинаковые
даты, числовые/строковые ID, отсутствие брони, фильтры, дубликаты клиентов,
старые статусы и повреждённые строки чата, свежесть после внешнего изменения
и отсутствие записи в файлы. Сравнение на локальных данных также проверяет
равенство старых/новых ответов для периодов и вкладок.

Production не изменялся. Для применения этого изменения нужен выпуск
backend-кода и отдельный перезапуск обслуживающего API процесса владельцем;
одного обновления frontend недостаточно. Сервисы агентом не перезапускались.

# Общий Telegram-бот парков: первый пакет

Реализовано в исходниках 9 октября 2026 года. Это основа входа и привязки Telegram,
а не готовая интеграция календаря/CRM/Алисы. Production не изменялся, webhook не
регистрировался, реальный токен не использовался для сетевых запросов.

## Упрощение для пилота

- Суперадминистратор управляет платформой через существующую защищённую сессию.
- Владелец получает полный уровень доступа только к своему парку (`owner`).
- Клиент получает свою привязку к парку, без административных прав.
- Один парк может иметь несколько владельцев с одинаковым доступом. Общий пароль
  или общий Telegram-аккаунт не требуются.
- Детальные роли сотрудников, экран управления правами и парольный вход отложены.
  Membership сохраняется отдельно от клиента: будущие роли не потребуют смешивать
  административную и клиентскую идентичность.

## Что работает в коде

1. Публичная ссылка `https://t.me/<username>?start=p<tenantId>` открывает нужный парк.
2. Бот принимает `/start` только из личного чата с подтверждённым Telegram-отправителем.
3. Сохраняется отдельная привязка `bot_id + tenant_id + user_id + chat_id`.
4. Бот отправляет кнопку Mini App на существующий `/p/<tenantId>`.
5. Владелец подключается отдельным случайным приглашением на 24 часа.
   Выдача прав одноразовая. После активации эта же ссылка открывает парк
   только тому же активному владельцу, в том числе после истечения срока
   активации. Чужой аккаунт и отключённый владелец не могут использовать её.
   Использованные ссылки сохраняются в пределах существующего лимита 1000
   записей; отзыв ссылки удаляет этот способ входа, но не сами права владельца.
6. Приглашение может быть заранее ограничено конкретным Telegram user ID, но это
   необязательно: парк и автомобили можно подготовить до знакомства с владельцем.
7. Свежая подписанная `initData` нового бота проверяется сервером; клиентские
   `chat_id`, `user_id` и `role` не принимаются как источник прав.
8. Суперадминистратор может отозвать приглашение и отключить владельца. Проверки
   прав читают актуальное membership, поэтому отзыв действует сразу.

Простой `/start` без параметра просит открыть ссылку нужного парка. При нескольких
парках система не выбирает «последний» автоматически. Свободные сообщения пока
получают явный ответ, что диалоги с менеджером ещё не подключены.

## API

Все маршруты имеют префикс `/api/partners`:

- `GET /parks/{tenantId}/bot-link` — публичная ссылка только для `trial`/`active`.
- `POST /parks/{tenantId}/owner-invitations` — Bearer-сессия суперадминистратора;
  тело `{}` либо `{"expected_user_id":"123456789"}`. Ответ содержит `url`,
  `invitation_id`, `expires_in`.
- `DELETE /parks/{tenantId}/owner-invitations/{invitationId}` — отзыв приглашения,
  только суперадминистратор и только в указанном парке.
- `DELETE /parks/{tenantId}/owners/{telegramUserId}` — отключение владельца,
  только суперадминистратор. Отключённый владелец может оставаться обычным клиентом.
- `POST /identity` — `{ "tenant_id": "phuket-drive", "init_data": "..." }`;
  проверяет подпись нового бота и ранее установленную привязку. Возвращает только
  собственную идентичность и текущий уровень доступа. Не выпускает browser/Bearer
  сессию; не является календарным или booking endpoint.
- `POST /webhook` — только Telegram с правильным секретным заголовком
  `X-Telegram-Bot-Api-Secret-Token`; тело ограничено 64 KiB.

В React-суперадминке, внутри парка, добавлен блок «Telegram парка»: подготовка,
копирование и отзыв личного приглашения, срок действия и отдельная клиентская ссылка.
Пока приглашение активно, повторное создание блокируется: сначала отозвать ссылку
или дождаться истечения срока. При недоступном Clipboard API ссылка выделяется
для ручного копирования. Секретная ссылка хранится только в состоянии компонента,
не в localStorage или URL текущей страницы; после выхода из парка она исчезает.
Отзыв уже выданного owner membership по-прежнему доступен через административный API,
но не через новую кнопку отзыва приглашения.

На публичной витрине добавлено открытие бота и проверка `/identity`, если Telegram
передал непустую `initData`. Результат проверки показывает клиентский/owner-доступ,
но не разрешает операции только на основании состояния UI. Ошибки неправильного
бота/привязки/истёкшей подписи предлагают заново открыть парк в правильном боте.
Выключенный бот показывает понятное сообщение, не мешая просмотру каталога.
В закрытом превью блок подключения не появляется. Витрина остаётся read-only.

## Данные и защита

`backend/data-v2/platform/control-plane.json` дополнен полем `partner_bot`:
привязки, хеши приглашений и журнал ответов. Сырые секреты приглашений и bot token
в нём не хранятся. Invitations, membership и отметка обработки update фиксируются
одним атомарным обновлением под общей межпроцессной блокировкой provisioning.
Существующие операции provisioning сохраняют новое поле.

Membership использует `telegram:<botId>:<userId>`, чтобы случайно не дать владельцу
нового бота права по старому идентификатору другого канала. Клиентская ссылка и
bare tenant ID никогда не создают membership. У черновика можно подключить владельца,
но не получить общедоступную витрину; suspended/cancelled/archived закрыты.

Неограниченное конкретным user ID приглашение — bearer-секрет: доступ получает
первый открывший. Отправлять его лично владельцу, не публиковать и не пересылать
в общую группу. Если ссылка утекла — отозвать; если уже использована — отдельно
отозвать owner membership. Отзыв приглашения не снимает ранее выданные права.

Повторы update в пределах 48 часов не создают повторных membership или ответов.
Неотправленный ответ хранится и повторяется при webhook retry; отправка под lock
сериализует параллельные повторы. После неоднозначного сетевого timeout Telegram
может получить повторный ответ: exactly-once отправка не обещается. Независимый
outbox worker пока отсутствует; успешная доставка зависит от повторов webhook.
Для пилота это достаточно, но при росте нужна отдельная очередь: сетевой запрос
держит control-plane lock до 10 секунд. Лимиты: 1000 активных приглашений и 10000
ответов в retained-журнале. Секретные URL Telegram не попадают в сообщения ошибок.

## Конфигурация и включение после отдельной публикации

Используются уже добавленные владельцем ключи `PLATFORM_PARTNERS_BOT_TOKEN` и
`PLATFORM_BOT_NAME`. Имя — username бота, а не его отображаемое название; `@` допустим.

Дополнительно необходим отдельный случайный `PLATFORM_PARTNERS_WEBHOOK_SECRET`
(32–256 символов base64url), `PLATFORM_PARTNERS_BOT_ENABLED=true` и HTTPS-origin
`PLATFORM_PARTNERS_PUBLIC_ORIGIN` (по умолчанию `https://sunny-rentals.online`).
Авторизация суперадминистратора использует существующие `PLATFORM_ADMIN_*`.
Пример находится в `backend/.env.saas.example`; реальный `.env` не редактировался.

При выключенном флаге маршрут не подключается, хранилище не создаётся и polling
не запускается. При явном включении неполная конфигурация отклоняется при старте.
Для открытия витрины нужен также существующий `PLATFORM_ADMIN_API_ENABLED=true`.

После разрешённой публикации уполномоченный владелец отдельно регистрирует webhook
нового бота на `https://sunny-rentals.online/api/partners/webhook`, передавая тот же
секрет через `secret_token`. Существующий webhook Sunny менять нельзя. Этот пакет
не вызывает `setWebhook`, не запускает polling и не перезапускает сервисы.

Контракт deep links и секретного webhook-заголовка сверялся с первоисточником:
[Telegram deep linking](https://core.telegram.org/bots/features#deep-linking) и
[setWebhook](https://core.telegram.org/bots/api#setwebhook).

## Проверки и следующий пакет

`backend/tests/test_platform_partner_bot.py` — временные данные, фиктивный Telegram,
без сетевой отправки реальным токеном. Покрыты подпись другого бота, отсутствие
прав, изоляция парков, срок и однократность приглашения, гонка потребления,
отзыв доступа, повторы update, retry отправки, группы/поддельный chat ID, черновики,
закрытые парки, атомарный сбой сохранения и сохранение состояния при provisioning.

Следующим этапом: tenant-scoped бронирование и календарь, группа диалогов, затем Алиса с данными
только этого парка. Глобальные Sunny booking/CRM endpoints не подключаются напрямую
к новому боту: сначала им нужны tenant-aware адаптеры.
